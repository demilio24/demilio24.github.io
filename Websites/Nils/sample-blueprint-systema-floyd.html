Specific data risks we observed

Expand each to see what we saw and why it matters.

If the routing logic between GHL and the sheets misses one week, the kid shows up Monday and the staff has no record. There is no automated catch for this today.

Across a busy week we found at least three instances of the same family being charged different amounts on different rows.

A waiver signed in one system does not write back into the roster. During the audit we found at least one student on a roster with no waiver matched, and one waiver with no matching roster entry.

Staff manually correct a billing row in GHL; it gets overwritten the next time the contact submits a form. The current system has no way to express "this manual edit beats the form."

Roster rows are categorized by which tab they live in (one tab per week). Inserting a new tab anywhere in the sequence silently shifts every downstream tab's meaning. This has happened: multiple billing rows got assigned to the wrong week.

GHL tokens stop refreshing if the upstream automation fails. Staff finds out only when a workflow that depended on the token stops working.

What is working today (do not break)

  • GoHighLevel for marketing, calendars, contacts. Forms, booking, and CRM stay.

The failsafe pattern

Every primary writer has a secondary watcher.

This is the single most important architectural decision in the system. Even if every bot dies, the source of truth (Sheets) is editable by hand, and the manual paths are first-class entry points, not exception handlers. It is what lets us promise the team they will not lose work.

Primary writerFailure modeWatcher does
GHL routing workflowMisfires, field maps wrongDiscrepancy Check writes the missing row, emails the owner
Billing pipelineApps Script quota hitManual Items dialog as backup ingress
Snapshot pushToken expired, push failsHeartbeat guard emails the owner if snapshot is >24h stale
Waiver MatcherApps Script disabledOperator annotates by hand without breaking the flow
Snapshot.jsonRepo corruptedRoll back to any prior day's archive
Why backups are the spine, not an afterthoughtA single point of failure that quietly misses a write is the worst thing that can happen to this school: nobody notices for a week, and by then the data is gone. So every writer has a watcher, every watcher has a heartbeat, and the source of truth stays hand-editable even if every bot dies. We would rather run a 15-minute cron forever than lose one registration in enrollment season.

Component Specifications

The build-ready detail for each subsystem. Expand any component for its inputs, outputs, parts, and the key decisions behind it.

Purpose. Convert every form submission into a structured row in the right roster sheet, in the right tab, with the right columns. Catch any missed write within 15 minutes.

Inputs
  • Free Camp form submissions
  • Summer Camp form submissions
  • After-School form submissions
Outputs
  • One row per kid-per-week-per-program
  • Optional cell note with parent's free-text info
Components

GHL routing workflow: one workflow per camp-week pair. Camp Day Validator: client-side JS that checks the right number of day boxes before submission. Discrepancy Check: Apps Script (15-min cron) that diffs every GHL submission against every roster row and patches misses. Tombstones: Supabase table recording intentional deletes so they stick.

Key decision. Source of truth is the sheet, not GHL. Name-based week resolution (by tab name, not position). Fuzzy-name dedup at a Jaro-Winkler threshold of 0.92.
Why we built it this wayWe trust the sheet over GHL on purpose: the team can fix a row in two clicks, and a workflow that silently misses a write is the one failure that costs you a kid showing up Monday with no record. The 15-minute watcher exists so that miss is caught and patched before camp opens, not discovered the next week. The grace window and tombstones mean it never fights the team: it won't double-add a row, and it won't resurrect one you deleted on purpose.
  1. One GHL routing workflow per camp-week pair fires on submission and runs an Add Row to Sheet action into the correct weekly tab.
  2. A client-side Camp Day Validator in the form blocks submission until the ticked day-count matches the chosen duration, so the billing math downstream is always right.
  3. Every 15 minutes the Discrepancy Check reads every GHL submission and diffs it against every roster row, skipping anything younger than a 5-minute grace window so it never races the workflow.
  4. A submission with no matching row past the grace window is auto-appended to the correct week, stamped with a source note, and recorded in a form_submissions table so it can never be added twice.
  5. Names match with Jaro-Winkler similarity (≥ 0.92) plus exact and single-token fallbacks, so "Aria" and "Aria Falzone" on the same parent email are one student, not two.
  6. An hourly auto-merge collapses high-confidence in-tab duplicates (≥ 0.95); anything below threshold is emailed for a human to review, never merged blindly.
  7. If the watcher itself goes quiet, a heartbeat guard notices within 24 hours and emails the owner. The backstop has a backstop.

Purpose. Prevent parents from submitting with the wrong number of days picked, which keeps the downstream billing math correct.

Implementation. A self-contained JavaScript snippet in the GHL form's Custom Code element. Re-attaches change handlers on every DOM mutation (GHL re-renders the form on conditional logic), reads the "Camp Duration" dropdown, counts checked day boxes per week, and blocks submission until they match.

Why client-side. The form is already in GHL and the browser is already executing code there. Server-side validation would mean standing up a custom backend in front of GHL for no benefit.

Purpose. The operator's single view of who is enrolled, who is here, who needs what lunch, and what is leaking.

Inputs
  • The 4 roster sheets
Outputs
  • snapshot.json (read by the browser)
  • Daily history archive
  • Supabase mirror tables

Snapshot.js polls the rosters every 5 minutes, builds the JSON, pushes to GitHub Pages, mirrors to Supabase. The browser dashboard renders KPIs (enrollment, capacity %, lunch orders, allergies), a 14-day sparkline, a filterable roster, a Data Issues panel that deep-links to the offending cell, an attendance modal with per-person ticks, and a lunches prep view.

Key decisions. Static hosting (loads in 200ms, no backend). Read-only by default. Per-person attendance with bulk operations, synced across devices via the database. Deep-linkable data issues: every anomaly has an "Open ↗" that lands on the exact cell.
Why we built it this wayStaff do not want another app to log into at 6am. They want to glance at one screen and know who is coming and who needs what lunch. So the dashboard is read-only by default (the sheets stay the write path), it loads in a fraction of a second because it is just static files, and the one thing staff do write, attendance, syncs live so the front desk and the kitchen see the same picture.
  1. A Snapshot script reads the four roster sheets every 5 minutes, resolves each tab to its canonical week label by name, and aggregates totals, by-campus, by-week, lunches, and allergies.
  2. It writes one snapshot.json to GitHub Pages (live) plus a dated history/YYYY-MM-DD.json archive, and mirrors the rows into the database. The mirror is non-fatal: a database hiccup never blocks the dashboard.
  3. A 2-minute lock serializes runs so two triggers can never double-write the same snapshot.
  4. The browser dashboard fetches snapshot.json (no-cache) every 60 seconds and renders KPIs (unique students + a 14-day sparkline, occupancy %, per-campus, top week), a donut + stacked bars, and a filterable week-card roster with Mon-Fri chips.
  5. Attendance records two ways: a totals mode (Upper / Lower / Free) and a by-person mode with present/absent toggles. Each tick writes to the database keyed by a stable person key, so picks survive every snapshot refresh and sync across devices in real time.
  6. Every data anomaly (missing field, no waiver) becomes its own card with an Open ↗ that deep-links to the exact source cell. No more "we know there's a problem but can't find the row."

Purpose. The canonical financial record. Every enrollment priced, every payment recorded, every refund tracked, balance always current.

Inputs
  • 4 roster sheets
  • Pricing catalog (team-editable)
  • Manual Items tab (cash, scholarships, refunds)
  • GHL Transactions API (FL/GA/VA)
Outputs
  • Billing Dashboard sheet (canonical)
  • GHL contact upserts (phones, tags)

BillingFromSheets.js (every 5 min) prices each enrollment, applies sales tax by state (FL 6%, GA 4%, VA 5.3%), inflates with the GHL processing fee, and applies the diff with proper lifecycle (new → owed, dropped → canceled, paid-then-dropped → refund-needed). Manual Items dialog writes non-form rows with a stable fingerprint. RemoteTrigger.js exposes admin RPCs over authenticated HTTPS.

Key decisions. Fingerprint-based reconcile (email + product + period), not submission-ID. Sheet is canonical, manual edits beat the form. Idempotency on every operation. Hierarchical row grouping by family.
Why we built it this wayBilling is where trust lives or dies. The owner needs to open one sheet and believe the balance. So we never let an automated run overwrite a human correction: rows are matched by a content fingerprint, not a form ID, which makes cash payments, scholarships, and manual fixes first-class rows, equal to anything a form created. Every operation is idempotent, so re-running the pipeline after an outage can only converge on the truth, never corrupt it.
  1. Every 5 minutes the pipeline walks the registration sheets plus a hidden Manual Items tab and prices each enrollment against a team-editable Pricing catalog (read at runtime, no redeploy to change a price).
  2. For each enrollment it generates up to five line items: tuition, lunch, breakfast, before/after care, and a one-time t-shirt, applying the per-day or per-week multiplier from the catalog.
  3. Price is inflated inline: taxable goods get sales tax by state plus the processing fee; everything else gets the processing fee only. No separate fee rows clutter the sheet.
  4. It reconciles by diff: each row is keyed by a fingerprint (email|student|week|item). New fingerprints append under the family; missing ones flip status (owed → canceled, paid → refund-needed) and are never deleted.
  5. A Manual Items dialog lets the operator add a cash payment, scholarship, or refund; it writes to the hidden tab and a one-time trigger lands it on the dashboard within seconds.
  6. Customer rows are parent rows, transactions are children, so a family's balance collapses to one line. An admin web app exposes whitelisted recovery actions (rebuild, restore links, dedup) behind a token.
  7. When the team marks invoices in GHL, a paid-sync reads GHL's paid invoices and flips matching rows owed → paid, closing the loop without anyone re-typing.

Purpose. Route after-school enrollments from a single central intake into the right per-school spreadsheet.

An Apps Script bound to the Main Table reads the school name on every new row and writes it into the matching destination. Auto-create on first use: a new school gets a destination sheet built from a template. Three-tier name matching: exact → case-insensitive → Levenshtein fuzzy ("Lincoln Elem." vs "Lincoln Elementary" vs "Lincoln").

Key decision. Each school's sheet is independent. The administrator gets read access to their sheet only. The Router is the only piece with access to all of them.
Why we kept the schools isolatedA partner school's principal should see their kids and only their kids. One sheet per school means a permission can never leak across schools, and a school that leaves takes nothing of anyone else's with it. The Router is the single trusted broker that sees all of them, and the three-tier name match means a typo in the school name still lands the row in the right place.

Purpose. Cross-reference signed waivers with roster entries. Surface allergies and health notes inline on the roster so staff sees them before camp starts.

An Apps Script bound to the Waiver app sheet fuzzy-matches student names by email + Jaro-Winkler similarity. Matched cells get a green background; unmatched stay white, so staff can scan a roster and see who is missing a waiver at a glance. Cell notes carry allergy info, medication notes, and emergency contacts inline.

Key decision. Waivers and rosters stay separate sheets with the matcher running between them. They have different access controls and lifecycles, so merging was rejected.
Why this is a safety feature, not a convenienceAn instructor opening the roster on camp morning needs to see "severe peanut allergy" without hunting through a second system. So the matcher pushes the health note onto the roster cell itself and turns matched cells green. Keeping the waiver app a separate sheet means its stricter access controls stay intact: we move the information, not the permissions.

Purpose. All public-facing pages that drive enrollments. Hosted on GitHub Pages, embedded into GHL via iframes with email passthrough, so they look like part of the GHL site.

Why Sheets, not a databaseWe looked hard at moving the school onto a real database. Sheets won. The team already lives there, anyone can fix a row in two clicks without a developer, and Google version-controls every change for free. We trade schema enforcement for the one thing that matters at this scale: the operator can correct their own data instantly. The code just has to read defensively, which it does.
  1. Each roster is one sheet per campus, with one tab per week named like 6/1-6/5.
  2. Every reader resolves a tab to its canonical week label by name, not position, so inserting or reordering a tab never silently re-files rows into the wrong week (a real failure we watched happen before this fix).
  3. The Pricing catalog is a tab on the Billing sheet: six columns (category, item, price, multiplier, source, aliases). Prices are read at runtime, so the team changes a price by editing a cell, no developer, no redeploy.
  4. A hidden Manual Items tab is the supported path for anything a form did not create: cash, scholarships, refunds.
  5. Adding a new week is one line in the week-order list plus a push. Both the dashboard and billing read tabs by name, so tab position is irrelevant.

Why a database at allSheets are perfect for the team to edit but bad at two things: real-time state shared across devices, and remembering a decision after a row is deleted. That is what the database is for. It holds live attendance (so the front desk and kitchen agree), tombstones (so a delete the team made on purpose is never undone by a bot), and a heartbeat log (so we know the bots are alive). Nothing customer-facing lives here; it is the system's shared memory.
  1. The tables hold only what Sheets cannot: a roster mirror, daily snapshots, live attendance, submission and merge tombstones, a bot-health heartbeat, and the staff/role table.
  2. Read paths are public (the dashboard reads attendance with no login); write paths require a shared secret, so only our scripts can write.
  3. Attendance is keyed by a stable person key (name + email), so a tick survives every 5-minute snapshot refresh and appears on every device instantly.
  4. Clearing a tick hard-deletes the row (no row means "not recorded"), while the tombstone tables are append-only, so a deliberate decision is never forgotten.
  5. Dashboard access is row-level: a trigger seeds a staff row on first login with no access until an admin grants pages, and every page re-checks the role.

Decision Log

The key architectural decisions and why we made them. Expand each for the reasoning and the tradeoffs we accepted.

Why. The team already lives in Sheets and can edit it without a developer. Trading that flexibility for a "real database" would turn every fix-one-row request from a 30-second edit into a developer ticket.

Tradeoffs accepted. No schema enforcement (so validation is defensive in every reader). Rate limits (so we polite-cache instead of polling aggressively).

Why. Apps Script binds natively to the sheets, deploys in seconds, costs nothing, and runs server-side without us managing infrastructure. n8n stays only for OAuth token refresh, where its cross-domain story beats Apps Script.

Tradeoffs accepted. Execution quotas: every job is idempotent and chunked so a quota hit never corrupts state.

Why. Manual rows, cash payments, and legacy imports have no submission ID. A fingerprint of email + product + period makes manual and automated rows equal first-class citizens.

Tradeoffs accepted. Collisions are possible; a content-hash on each row gives de-dup safety.

Why. We watched the positional model break in production: inserting a tab shifted every downstream tab's meaning. Name-based resolution survives reordering, insertion, and deletion.

Tradeoffs accepted. Tab names must follow a documented format; the runbook covers the rename procedure.
